# Repository audit and model decisions

Audit performed before implementation on the existing working tree; no Git reset or framework migration. Existing uncommitted theme/dashboard/admin-directory changes were retained as the starting point. Inspection covered all repository pages, JavaScript modules, CSS/theme, Firebase configuration, manifest, README, rules and Hosting settings. No AGENTS.md was found in the workspace tree. The live Firestore database was not accessed; schema was inferred from source.

1. **Already implemented:** Email/password login, role redirects, student dashboard/profile/local photos, automatic request preview, shared Stage 1 desk, mentor/HOD decisions, office search/issuance, theme toggle; a basic admin student directory and CSV import existed in the working tree.
2. **Original collections:** `users/{uid}` held roles and student/staff profile fields; `students/{uid-or-USN}` was a separate CSV directory; `noDueRequests/{requestId}` held student/academic snapshots, mentorId, status, mentorApproval/hodApproval, createdAt and issuance details; nested `approvals` held approverType, subjectCode, label, status, remarks, actedBy/actedAt and student/request fields.
3. **Roles:** student, subject_faculty, library, physics_lab, chemistry_lab, accounts, mentor, hod, office; admin login routing already existed but the admin page lacked an auth guard and its writes were denied by original rules.
4. **Workflow:** Stage 1 parallel approvals → mentor → HOD → cleared → office issued. Existing statuses are retained exactly.
5. **Rejection/resubmit:** Stage 1 remarks were recorded and client `checkAndAdvance` changed request status after a separate write. Resubmission reset rejected items, preserving approved items; mentor/HOD rejections resumed their own stage. Student status UI did not show detailed Stage 1 rejection reasons or private events.
6. **Existing files needing changes:** auth, workflow, student/create-request, shared approver/mentor/HOD/office modules, admin page/module, Firebase config/rules/Hosting config, dashboard navigation, shared stylesheet and README. Full final inventory is in CHANGES.md.
7. **New modules/views:** one shared academic page/module, academic data access, admin data helpers, HTML-safe UI helpers, private student updates, pure workflow state helpers, robust CSV helper, indexes, isolated emulator tests/fixtures and documentation. Shared pages avoid duplicating student/teacher/mentor academic logic.
8. **Security/architecture findings:** all authenticated users could read users/requests/approvals; broad student/mentor/HOD/office update permissions allowed stage or ownership tampering; Stage 1 request advancement lacked permission and was a separate race-prone operation; approval creation had no matching rule; subjects defaulted to hard-coded semester 6-B; student directory conflated USN with Auth UID; mentor loaded the entire directory and treated unassigned students as mentees; directory CSV did not properly parse quoted fields; listeners lacked cleanup; several queues had no bounds; marks/assignments/index configuration did not exist; manifest referenced absent icon files. No frontend secrets beyond ordinary public Firebase web config were introduced.

## Final model rationale

`users` remains the authority for roles and staff/mentor profiles. `students/{authUid}` becomes the centrally managed canonical student academic profile. A subject is stable across sections; an offering associates that subject with semester, section, teacher and assessment components. Enrollments link actual Auth UIDs to offerings. Marks use the enrollment document ID and current trusted mappings for authorization. Assignments attach to an offering. Mentor/student relationships are verified using the current student document.

Admin prepares a bounded clearance plan from active enrollments and institution-level service UIDs. New requests copy that trusted plan; rules reject client substitutions and academic snapshot changes. A bounded approval-state map plus counter permits secure, atomic Stage 1 advancement without a paid server function. Existing nested approval documents are maintained as audit projections; queues query request `approverIds` so omitted client projections cannot hide required approvals or authorize a bypass. Notifications are immutable, transaction-bound events under the owning UID.

Rules use field diffs and `getAfter` to validate atomic changes, following Firebase's [transaction rules documentation](https://firebase.google.com/docs/firestore/manage-data/transactions) and [field restriction documentation](https://firebase.google.com/docs/firestore/security/rules-fields). Query constraints match rule predicates, following [secure query guidance](https://firebase.google.com/docs/firestore/security/rules-query). Actual rules and authorized/denied SDK calls were exercised against the local Firestore emulator.
